# Renault Reader engineering notes

- Bun + TypeScript strict + ESM NodeNext; relative TS imports include `.js` suffixes. Layout copies `mercedes-reader`/`bmw-reader`: `domain/`, `application/` (ports, use-cases), `infrastructure/`, `interfaces/http/`, `composition/`.
- This service extracts from ASMDOR (Renault's A5M portal API): it requests the exports, waits for them, downloads them and stores them **raw** in S3 with a manifest v2 written last (`{unit}_completed.json`, Renault-specific content under `details`). Keep business transformations (Access rules, applicability/HTC, hashes, Acciona SQL, Excel, comparisons, parsing of the archives for the data model) out of this reader: they live in `renault-transformer` (pending adaptation to core-reader's transformer contract). The only thing read from a stored archive is REF04/REF05, to derive the PR08/PR03 families (`application/use-cases/derive-families.ts`); the stored files are never modified.
- Shared contract and infrastructure come from `@pablosla/core-reader` (HTTP v1 contract, routers, errors, Redis client, state, locks, worker runtime, index, token pool, S3, BullMQ, cancellation flags, run heartbeat, `extractionFolder`/`pathSegment`, manifest). Do not copy those pieces here; improve them in `reader-core` instead. The version is pinned exactly (0.6.0), like every other dependency.
- Internal request states use core-reader's `RequestStatus`; persist queue references as `queueJobId`. The real `ApplicationError.code` of a failure is stored (`errorCode`) and mapped; default `INTERNAL_ERROR`.
- Resources: `labours` = one TM01 export; `parts` = the legacy "model" extraction (REF04, REF05, optional REF01/REF02/REF03/PR05/PR06, then PR08 and PR03 per family derived from REF04 x REF05). One BullMQ job is one export (a *unit*); the next job is queued after the previous unit is persisted. A unit whose manifest already exists is reused without calling Renault, which is what makes `/resume` and recovery cheap.
- Credentials come only from `RENAULT_EMAIL` / `RENAULT_PASSWORD` / `GIGYA_API_KEY`. The legacy Access VBA embedded credentials; they are exposed and must be rotated, never copied. Never log tokens or passwords.
- Auth: Gigya `accounts.login` (form: apiKey, loginID, password, sessionExpiration=600, pageURL) then `POST v1/user/gigya/accessToken` with the signed identity; API calls send `Authorization: Bearer`. It is not OAuth client-credentials, so it only reuses core's `AccessTokenPool` (see `infrastructure/renault/client.ts`). The presigned download URL must not receive the bearer token.
- Cancelling never deletes S3 data and never aborts a request already sent: it only stops new requests and interrupts the History waits. A worker shutdown pauses the request (`paused`) and the next worker requeues it.
- `queryService`, `queryDownloadPath`, families, formats and languages come from the authenticated upstream; do not assume them. Family authorisation rules (partner vs editor accounts) are those of the legacy flow.
- There is no rate limiter: ASMDOR has no documented quota; load is bounded by `JOB_CONCURRENCY` and the History polling interval.
- Integration tests (`bun run test:integration`) use Docker with ports 46379 (Redis) and 49000 (RustFS) and never call real Renault. Never call the real Renault APIs from tests.
- Docs are in `docs/` (Spanish): `docs/asmdor-api.md` (API findings), `docs/s3-layout.md` (what the transformer consumes). Legacy Access rules live in `renault-transformer/docs/access-api-alignment.md`.
